## Issues Found

### Minor Issues (Non-Critical)

#### Issue 1: Uniqueness Validation Relies on Database Constraints
**Location:** `lib/db/queries.ts` - `createEmployee()` (line 1249) and `createBenefitsPlan()` (line 1510)

**Description:** Both functions don't perform explicit uniqueness validation for email/employeeId and planId respectively. They rely on database unique constraints to throw errors.

**Impact:** Low - Database constraints will prevent duplicates and throw errors, but error messages may not be user-friendly.

**Recommendation:** Consider adding explicit validation with better error messages, or document that database constraints handle this.

**Severity:** MINOR

---

#### Issue 2: Inconsistent Data Fetching in getEnrollmentByEmployeeId
**Location:** `lib/db/queries.ts` - `getEnrollmentByEmployeeId()` (lines 1634-1642)

**Description:** This function only returns the base enrollment record, while `listEnrollments()` fetches full plan details and dependents.

**Impact:** Low - Callers may need to make additional queries to get plan details.

**Recommendation:** Update `getEnrollmentByEmployeeId()` to fetch full details for consistency.

**Severity:** MINOR

---

#### Issue 3: conflictsWith Array Not Resolved to Names
**Location:** `lib/db/queries.ts` - `listLeaveRequests()` (lines 2137-2196)

**Description:** The plan mentions "Resolve conflictsWith array to employee names" but implementation returns employee IDs only.

**Impact:** Low - Frontend will need to resolve IDs to names separately.

**Recommendation:** Add join logic to resolve employee IDs to names if needed by UI.

**Severity:** MINOR

---

#### Issue 4: No Transaction Usage in seedAllHRData
**Location:** `lib/db/seeds/hr-data.ts` - `seedAllHRData()` (lines 964-1006)

**Description:** The plan states "Use transactions if possible" but implementation doesn't use transactions.

**Impact:** Low - Partial data on failure, acceptable for demo purposes.

**Recommendation:** Consider wrapping in transactions if Drizzle ORM supports it easily.

**Severity:** MINOR

---

#### Issue 5: Reset to Defaults Has No Confirmation Parameter
**Location:** `trpc/routers/admin.router.ts` - `hr.resetToDefaults` (lines 975-991)

**Description:** The plan notes "Consider adding a confirmation parameter" but procedure runs without confirmation.

**Impact:** Low - Admin-only access, but accidental resets possible.

**Recommendation:** Add confirmation parameter (e.g., `confirmDelete: z.literal("DELETE_ALL_DATA")`).

**Severity:** MINOR
