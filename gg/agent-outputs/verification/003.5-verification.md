## Issues Found

### Critical Issues

#### 1. HR Case Tool - Missing "update" Action
**Severity:** Critical
**Location:** `lib/ai/tools/hr-case.ts` lines 234-236
**Description:** The phase plan (Section 3.7) requires an "update" action to be implemented, but the tool's input schema only allows `["create", "status", "list"]`. The database function `updateHRCase` exists in `lib/db/queries.ts` but is never imported or used.

**Impact:** Users cannot update existing HR cases through the tool, even though the admin panel likely supports this functionality. This breaks the bidirectional data flow promise.

**Recommendation:**
```typescript
// Add to inputSchema enum
action: z.enum(["create", "status", "list", "update"])

// Add to dynamic imports
const { ..., updateHRCase } = await import("@/lib/db/queries");

// Implement UPDATE action handler
if (action === "update") {
  if (!caseId) {
    return { error: "Case ID is required to update" };
  }
  // Update case logic
  const updated = await updateHRCase(caseId, { status, priority, ... }, updatedBy);
  return { action: "update", case: transformedCase };
}
```

### Major Issues

#### 2. People Search - Limited Search Functionality
**Severity:** Major
**Location:** `lib/ai/tools/people-search.ts` line 159
**Description:** The tool only searches by "fullName" field, but the phase plan (Section 5.4) requires support for multiple search fields including "all" which should search across name, title, department, skills, and location.

**Current Implementation:**
```typescript
const dbEmployeesResult = await listEmployees({
  searchValue: query,
  searchField: "fullName", // Only searches by name
});
```

**Expected Behavior:** Should handle searchField parameter and support cross-field search when searchField = "all".

**Impact:** Users can only search by employee name, not by title, department, or other attributes. Tool description promises "Search employee directory by name, title, department, skills, or location" but doesn't deliver on this promise.

**Recommendation:** Implement proper search field handling or add multi-field search capability to the listEmployees query function.

#### 3. People Search - Hardcoded Default Values
**Severity:** Major
**Location:** `lib/ai/tools/people-search.ts` lines 211-220
**Description:** Many employee fields return hardcoded defaults instead of actual database values:

- `hireDate`: Always `new Date().toISOString()` instead of `emp.startDate`
- `startDate`: Always `new Date().toISOString()` instead of `emp.startDate`
- `yearsOfService`: Always `0` instead of calculated value or `emp.yearsOfService`
- `workAuthorization.status`: Always `"citizen"` instead of actual data
- `workAuthorization.expiryDate`: Always `undefined`
- `probationEndDate`: Always `undefined` even when employee is on probation
- `terminationDate`: Always `undefined` even when employee is terminated

**Impact:** The People Search tool returns incomplete and potentially incorrect employee information, undermining the accuracy of the HR data system.

**Recommendation:** Map all employee fields from database records properly. Review database schema to ensure all necessary fields exist.

#### 4. Benefits Info - Semantic Field Mismatch
**Severity:** Major
**Location:** `lib/ai/tools/benefits-info.ts` line 220
**Description:** Dental plan enrollment uses `coverage?.annualMaxBenefit` for the `deductible` field:

```typescript
deductible: coverage?.annualMaxBenefit,
```

This is semantically incorrect - an annual maximum benefit is not the same as a deductible. A deductible is the amount the employee pays before insurance coverage begins, while the annual max benefit is the maximum amount the insurance will pay per year.

**Impact:** Users receive incorrect dental plan information which could lead to confusion about their coverage.

**Recommendation:** Either use the correct deductible field from the database or omit this field for dental plans if not applicable.

### Minor Issues

#### 5. Tool Descriptions Still Reference RBAC Restrictions
**Severity:** Minor
**Location:**
- `lib/ai/tools/team-availability.ts` lines 138-147
- `lib/ai/tools/people-search.ts` lines 107-122

**Description:** Tool descriptions still say "MANAGER-ONLY tool" and "HR-ONLY tool" with warnings about permission requirements, but RBAC checks have been removed from the code. This creates user confusion.

**Team Availability Description:**
```typescript
MANAGER-ONLY tool for viewing team availability and approving leave requests.
...
⚠️ IMPORTANT: This tool requires manager permissions. Only use when the user is a manager.
```

**People Search Description:**
```typescript
HR-ONLY tool for searching employee information and org structure.
...
⚠️ IMPORTANT: This tool is restricted to HR personnel only.
```

**Impact:** Users might think they don't have access to these tools when they actually do (as admin users).

**Recommendation:** Update descriptions to reflect that these tools are available to all admin users. Remove "MANAGER-ONLY" and "HR-ONLY" labels and permission warnings.

#### 6. Leave Balance - Potential Null Handling Issue
**Severity:** Minor
**Location:** `lib/ai/tools/leave-balance.ts` line 155
**Description:** The carryoverDeadline uses a fallback to current date when the database value is null:

```typescript
carryoverDeadline: b.carryoverDeadline || new Date().toISOString(),
```

This could be confusing if the actual policy doesn't have a carryover deadline. A null or explicit "No deadline" might be clearer.

**Impact:** Minimal - users might see today's date as a deadline when there isn't one.

**Recommendation:** Consider using a more explicit fallback like `null` or a special date value, or document this behavior.

#### 7. Benefits Info - Enrollment effectiveDate Field
**Severity:** Minor
**Location:** `lib/ai/tools/benefits-info.ts` line 192, 221, 245
**Description:** The enrollment effectiveDate is set to `enrollment.updatedAt`:

```typescript
effectiveDate: enrollment.updatedAt.toISOString(),
```

This is semantically questionable - the "updated at" timestamp is when the record was last modified, not necessarily when the benefits coverage became effective.

**Impact:** Users might see incorrect effective dates for their benefits enrollment.

**Recommendation:** If the benefits enrollment table has an `effectiveDate` field, use that instead. Otherwise, consider using `enrollment.createdAt` or document this design decision.

## Potential Bugs and Edge Cases

### Data Integrity Issues
1. **Missing employee record:** If hardcoded "EMP001" doesn't exist in database, all tools will fail
2. **Null/undefined handling:** Some fields use fallback values that might hide data issues
3. **Type mismatches:** JSONB fields require careful type casting

### Business Logic Issues
4. **Coverage calculation:** Team Availability coverage percentage calculated client-side might not match admin panel calculations
5. **SLA calculations:** HR Case SLA hours remaining might become negative for overdue cases
6. **Projection accuracy:** Leave Balance projections don't account for accruals between now and projection date

### Error Handling Gaps
7. **Database connection errors:** Tools will return generic error message without retry logic
8. **Invalid employee references:** Foreign key violations might not provide user-friendly messages
9. **Concurrent modifications:** Last-write-wins without conflict detection could cause data loss

## Performance Considerations

### Current Implementation
- Database queries are executed sequentially within each tool
- Some tools make multiple individual queries (e.g., Benefits Info fetches each plan separately)
- No query result caching implemented
- All tools use dynamic imports for queries (good for bundle size, small overhead at runtime)

### Potential Optimizations
1. **Benefits Info:** Could use a single query with joins instead of fetching each plan separately (N+1 query pattern)
2. **People Search:** Org chart building fetches full team member list even when not needed
3. **Team Availability:** Coverage calculation happens in-memory after fetching all absences (acceptable for small teams)

### Performance Expectations
Based on the implementation and phase plan requirements (FR-067):
- Tool database queries should complete in < 500ms
- Most tools appear to meet this requirement with simple queries
- Benefits Info might exceed this with large enrollments due to N+1 pattern
