## Database Schema

This phase establishes the complete database foundation with all tables matching the structure of the current mock data in the 5 HR tools.

### Table Definitions

**1. employee**
- Primary key: `id` (UUID)
- Foreign key: `userId` references `user.id` (one-to-one, cascade delete)
- Foreign key: `managerId` references `employee.id` (self-referential, nullable, set null on delete)
- Fields:
  - `id`: UUID primary key
  - `userId`: text, FK to user.id, unique, not null
  - `employeeId`: text, unique employee identifier (e.g., "EMP001"), not null, unique
  - `fullName`: text, not null
  - `preferredName`: text, nullable
  - `email`: text, not null (same as user.email, denormalized for convenience)
  - `phoneExtension`: text, nullable
  - `jobTitle`: text, not null
  - `department`: text, not null
  - `team`: text, nullable
  - `managerId`: UUID, FK to employee.id, nullable
  - `directReports`: json array of employee IDs, default []
  - `employmentStatus`: pgEnum, not null (values: active, probation, leave_of_absence, notice_period, terminated)
  - `location`: text, not null (e.g., "San Francisco HQ")
  - `workMode`: pgEnum, not null (values: office, remote, hybrid)
  - `officeLocation`: text, nullable
  - `workAuthorization`: json object with fields { status, expiryDate, requiresRenewal, daysUntilExpiry }
  - `startDate`: date, not null
  - `yearsOfService`: numeric(4,1), not null
  - `skills`: json array, default []
  - `certifications`: json array, default []
  - `expectedReturnDate`: date, nullable (for leave_of_absence status)
  - `probationEndDate`: date, nullable (for probation status)
  - `lastWorkingDay`: date, nullable (for notice_period status)
  - `createdBy`: text, FK to user.id, not null
  - `updatedBy`: text, FK to user.id, not null
  - `createdAt`: timestamp, not null, default now()
  - `updatedAt`: timestamp, not null, default now()
- Indexes:
  - Unique index on `employeeId`
  - Unique index on `userId`
  - Index on `employmentStatus`
  - Index on `department`
  - Index on `managerId`
  - Index on `email`

**2. leaveBalance**
- Primary key: `id` (UUID)
- Foreign key: `employeeId` references `employee.id` (cascade delete)
- Fields:
  - `id`: UUID primary key
  - `employeeId`: UUID, FK to employee.id, not null
  - `leaveType`: pgEnum, not null (values: vacation, sick, personal)
  - `currentBalance`: numeric(5,2), not null, check >= 0
  - `accruedYTD`: numeric(5,2), not null, default 0
  - `usedYTD`: numeric(5,2), not null, default 0
  - `accrualRate`: numeric(5,2), not null
  - `accrualSchedule`: pgEnum, not null (values: monthly, bi_weekly, quarterly, annually)
  - `carryoverLimit`: integer, not null, default 0
  - `carryoverDeadline`: date, nullable
  - `projectedYearEnd`: numeric(5,2), not null
  - `updatedBy`: text, FK to user.id, not null
  - `updatedAt`: timestamp, not null, default now()
- Indexes:
  - Composite index on `(employeeId, leaveType)` - unique
  - Index on `leaveType`

**3. blackoutDate**
- Primary key: `id` (UUID)
- Fields:
  - `id`: UUID primary key
  - `startDate`: date, not null
  - `endDate`: date, not null
  - `reason`: text, not null
  - `department`: text, nullable (null = applies to all departments)
  - `createdBy`: text, FK to user.id, not null
  - `createdAt`: timestamp, not null, default now()
- Indexes:

  - Index on `startDate`

**4. leavePolicy**

- Fields:

## Phase 1: Database Schema and Type Definitions

### Overview
Establish the complete database foundation for the HR Tools Admin Integration feature by defining all 12 tables, relationships, enums, indexes, and shared types.

### Important Codebase Context

#### Files that won't be modified but are important to understand
- `lib/db/client.ts:6-27` - Database client singleton pattern to follow
- `lib/db/queries.ts` - Where we'll add query functions in Phase 2
- `drizzle.config.ts:1-16` - Migration configuration
- `lib/db/schema.ts:203-218` - Existing user table that employee table will reference

#### Files that need to be modified or extended
- `lib/db/schema.ts` - Add all 12 new table definitions and pgEnums
- `src/types.ts` - Export all inferred types for use across the application

#### New Files that need to be created
- None in this phase (migration files will be auto-generated)

#### Patterns, Conventions, and Design Decisions to Reuse
- **Type Inference Pattern** (`lib/db/schema.ts:77-81`) - Use `InferSelectModel` and `InferInsertModel` for all types
- **UUID Primary Keys** (`lib/db/schema.ts:30`) - Use `uuid("id").primaryKey().notNull().defaultRandom()`
- **Timestamp Pattern** (`lib/db/schema.ts:67-68`) - Use `.defaultNow().notNull()` for audit timestamps
- **Foreign Key Pattern** (`lib/db/schema.ts:31-33`) - Use `.references(() => table.column, { onDelete: "cascade" })`
- **JSON Column Pattern** (`lib/db/schema.ts:36`) - Use `json("field").$type<TypeHere>()` for flexible data
- **Soft Delete Pattern** - Use status enums (e.g., employmentStatus = "terminated") instead of deletedAt timestamps

#### Key Constraints to work within
- All foreign keys to user table use `text` type (user.id is text, not UUID)
- All foreign keys to employee table use `uuid` type
- Use pgEnum for all enum types to ensure type safety
- Include audit fields (createdBy, updatedBy, createdAt, updatedAt) on all tables except join tables
- Enforce uniqueness on business identifiers (employeeId, caseId, requestId, planId)
- Add check constraints for data validation (e.g., currentBalance >= 0)
