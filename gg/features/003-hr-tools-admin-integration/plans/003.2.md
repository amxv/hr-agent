# HR Tools Admin Integration - Phase 2: Backend API and Data Layer

## Phase Overview

Build the complete backend API layer with tRPC procedures for all CRUD operations, database query functions, helper utilities, and the data seeding system. This phase provides the foundation for the admin UI (Phase 3-4) and tool integration (Phase 5).

**Dependencies**: This phase depends on Phase 1 being complete (all database tables created and migrated).

**References**:
- See `gg/features/003-hr-tools-admin-integration/summary.md` for the complete feature overview and implementation approach.
- See Phase 1 plan for Database Schema and Shared Type Definitions.

- `lib/hr/team-assignment.ts` - Team assignment configuration matching current mock data
- `lib/db/seeds/hr-data.ts` - Data seeding functions matching current mock data structure

#### Patterns, Conventions, and Design Decisions to Reuse
- **tRPC adminProcedure Pattern** - All procedures use `.use(adminProcedure)` for auth
- **Input Validation** - All inputs validated with Zod schemas
- **Dynamic Imports** - Query functions imported with `await import("@/lib/db/queries")`
- **Error Handling** - Use TRPCError with appropriate codes (UNAUTHORIZED, FORBIDDEN, BAD_REQUEST, NOT_FOUND)
- **Pagination Pattern** - Use limit/offset with total count for list queries
- **Search Pattern** - Dynamic WHERE clause with searchField and searchValue
- **Mutation Return Pattern** - Return `{ success: true, data: { ... } }` on success

#### Key Constraints to work within
- All mutations must track audit fields (createdBy, updatedBy using ctx.user.id)
- Soft delete for employees (set employmentStatus to "terminated")
- No optimistic locking (last-write-wins for concurrent edits)
- Simple validation: required fields, email format, uniqueness, non-negative balances
- SLA calculations based on creation date and category
- Coverage calculations based on team size and approved absences
